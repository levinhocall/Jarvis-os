# Canonical chat storage and safe legacy import

Baseline inspection: new service transcripts already used `ConversationRepository.appendTurn()` (Room). `MemoryManager.addShortTermTurn()` only maintained the bounded in-process context and learned facts via `MemoryRepository`/Room. It did not write legacy JSON. Therefore it needs no extra persistence writer; adding one there would duplicate the service writes. The remaining `ChatRepository.addTurn()`/`AppPreferences.saveChatHistory()` legacy writer APIs had no production callers and are now removed. The remaining facade is a read/clear import bridge, never a second active chat store.

Import runs from both application background initialization (including headless voice starts) and MainViewModel; the repository mutex serializes it with clear-history. Each attempt:

1. Reads the raw preference snapshot, distinguishing absent, valid empty and corrupt input. Invalid or partially valid records fail before any rows are written. The input is retained and a storage error is surfaced; no private text is logged by the importer.
2. Plans deterministic row IDs, retaining the previous `old:<turn ID>:<role>` identity. Missing IDs/timestamps receive deterministic values; repeated text in distinct turns is preserved.
3. Runs a Room `@Transaction`, inserting missing IDs with IGNORE (never overwriting existing messages), then rereads every expected ID and verifies role, text, timestamp and an existing parent session. Conflicts fail/roll back. Rows imported by the previous importer in another session are recognized by ID and preserved in their original session.
4. Only after transaction commit/verification, checks that the preference snapshot is unchanged and commits its removal. A crash before removal leaves the source for an idempotent retry. A clear failure also keeps the source where possible; no "migration complete" flag can hide an unverified import. An empty valid array can be removed without creating an empty Room session. Corrupt input is never treated as empty.

No schema version bump, new database, key change or destructive migration is introduced. Existing Room sessions, messages and user edits are preserved. New text/voice writes continue through the existing Room repository. The previous content-based importer may already have omitted repeated identical text before this change; text that was already erased from preferences cannot be reconstructed without a backup.

Tests: `LegacyChatMigrationTest` uses the existing in-memory `FakeChatDao` to exercise repository retries, source clearing, empty/absent/corrupt input, repeated text, stable missing fields, conflicting rows, readiness failure and clear-history behavior. The fake does **not** emulate Room transaction rollback; actual rollback/commit verification is covered by `ConversationRepositoryInstrumentedTest` and requires Android execution. Exact executed checks and any runtime limitations are recorded separately in the Phase A verification report.
